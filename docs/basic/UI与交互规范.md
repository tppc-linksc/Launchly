# Launchly UI 与交互规范

> **版本**：3.9
> **生效日期**：2026-08-13
> **地位**：Launchly 信息架构、关键页面、交互语义和视觉系统的唯一权威。产品对象与范围见[产品设计规范](./产品设计规范.md)，完成状态见[交付验收规范](./交付验收规范.md)。
> **当前实现**：`apps/web` 是过渡界面；现有顶栏、卡片、固定八步工作流或页面存在均不表示本规范完成。旧 `docs/prototypes/Launchly-prototype.html` 只作为历史风格参考，需按本版重做。

## 1. 体验目标

Launchly 应像“发布指挥台”，而不是资源 CRUD 后台。用户进入任何页面都应迅速回答：

1. 现在运行的是什么版本？
2. 流水线正在做什么，是否需要我行动？
3. 为什么被阻止或失败？
4. 下一步能做什么，操作影响什么？
5. 出问题时如何恢复到哪个已知良好状态？

### 1.1 设计原则

- **行动优先**：首屏优先等待审批、失败、回滚和节点异常，不用项目总数填充空间。
- **上下文完整**：Commit、Artifact、Config、Environment、Node、Gate 和 Release 在部署详情中可追溯。
- **真实状态**：固定说明步骤不能伪装成实际流水线；未连接的数据明确显示“未验收/未接通”。
- **中文诊断**：错误采用“现象 → 原因/影响 → 下一步 → 原始详情”四层结构。
- **渐进披露**：默认路径少字段；构建器、资源限制、路由和 Release Phase 放入高级设置。
- **密度适中**：运行页允许高信息密度，但通过层级、对齐和状态色组织，不堆独立卡片。
- **可访问**：状态同时使用颜色、图标和文字；键盘、焦点、对比度和屏幕阅读器可用。

## 2. 信息架构

### 2.1 全局工作域

全局导航保留六个稳定入口：

| 工作域 | 用户问题 | 核心内容 |
| --- | --- | --- |
| 指挥中心 | 现在什么最需要处理？ | 运行中、待审批、失败、回滚、节点/证书风险、下一步 |
| 应用 | 每个产品和环境运行什么？ | 应用、服务、环境泳道、当前制品、健康 |
| 部署 | 所有执行记录发生了什么？ | 队列、筛选、部署工作台、日志 |
| 环境 | 测试/预发/生产/Preview 有何差异？ | 环境策略、配置版本、域名、晋级、漂移 |
| 基础设施 | 应用运行在哪，节点是否健康？ | Node、容量、Agent/SSH、代理、诊断、排空 |
| 发布与质量 | 哪个制品可以进入生产？ | Release、门禁、证据、阻断项、审批 |

成员、密钥、通知、审计和系统设置放在用户菜单或“设置”，不占一级导航。

### 2.2 混合导航

- 全局使用顶栏或紧凑工作域导航，不使用宽灰侧栏承载所有资源。
- 进入应用后显示稳定的应用上下文导航：`概览 / 部署 / 环境 / 流水线 / 运行 / 质量 / 配置`。
- 复杂详情可以使用窄的上下文侧栏或右侧检查面板；这不等于全局后台侧栏。
- 面包屑必须显示 Workspace、Application、Environment/Deployment，避免用户失去范围感。

### 2.3 全局搜索与命令

全局搜索必须真正搜索应用、服务、部署 ID、分支、commit、域名和节点；不可只保留无行为输入框。支持 `⌘/Ctrl + K` 命令面板，提供“新建应用、触发部署、打开失败项、切换 Workspace”等动作，结果始终受权限过滤。

全局“部署”按钮先选择应用和环境，或在当前应用上下文直接打开部署面板；不能只跳转到部署列表。

## 3. 关键页面

### 3.1 指挥中心 `/`

桌面两栏布局：

- 主区：运行中部署、等待操作、最近失败/回滚的时间线。
- 侧区：节点/磁盘/证书风险、待审批发布、建议下一步。

每条事项至少展示应用、环境、阶段、持续时间、触发来源和主要操作。数字汇总只能作为筛选入口，不能替代任务列表。

空状态按首次路径显示：`连接仓库或镜像 → 验证节点 → 确认计划 → 首次部署`。

### 3.2 应用列表 `/applications`

默认表格或紧凑卡片，展示：应用名、服务数、测试/预发/生产当前版本、健康、最近部署、待处理项。支持按健康、环境、节点和来源筛选。

创建入口使用“新建应用”，旧 `/projects` 和“资源目录”在迁移期可重定向，但不能同时暴露三个含义重叠的一级入口。

### 3.3 应用总览 `/applications/:id`

顶部显示来源、默认分支、负责人、自动部署策略和主行动。主体使用环境泳道：

```text
测试                    预发                     生产
v1.8.4 · sha256:a1  →  v1.8.4 · sha256:a1  →   v1.8.3 · sha256:9f
健康 · 最新提交          等待审批                  当前流量
```

每个泳道展示当前 Artifact、ConfigRevision、域名、节点、健康、最近部署和与相邻环境的差异。晋级操作必须明确“复用同一制品”，不能叫“重新构建并发布”。

页面不再显示根据记录数量猜测的固定八步“工作流进度”。配置向导与真实部署流水线必须分开。

### 3.4 部署工作台 `/deployments/:id`

这是产品的核心页面，布局为：

1. **摘要栏**：状态、应用/服务、环境、commit/PR、Artifact digest、ConfigRevision、触发来源、执行人、耗时、访问地址。
2. **真实阶段图**：按后端阶段数据渲染，显示等待、执行、成功、失败、跳过、审批、回滚；点击阶段切换日志。
3. **日志区**：实时、可搜索、暂停跟随、按级别过滤、复制/下载；默认脱敏。
4. **右侧检查面板**：CI、测试、安全、审批、冻结窗口、制品签名及失败原因。
5. **差异区**：相对当前环境版本的 commit、Artifact、Config、域名、资源限制和 BuildPlan 差异。
6. **事件时间线**：Webhook、领取、重试、切流、回滚、通知和审计事件。

失败摘要必须先给可操作中文信息，再允许展开原始日志。若旧流量仍可用，应明确显示“当前线上未受影响”。

### 3.5 操作语义

| 操作 | 展示文案 | 必须提示 |
| --- | --- | --- |
| Restart | 重启当前实例 | 不改变制品和配置 |
| Redeploy | 重新部署此制品 | 不重新构建；重走部署和健康 |
| Rebuild | 从源码重新构建 | 产生新制品，可能不同 |
| Rollback | 回滚到所选成功版本 | 恢复制品、配置和路由快照 |
| Cancel | 取消部署 | 当前阶段能否安全取消、是否影响旧流量 |

危险操作显示目标环境、目标版本、影响和确认文本；生产操作需要权限和审计原因。

### 3.6 环境 `/applications/:id/environments`

环境详情包含：

- 自动部署分支、路径、CI、审批和并发策略。
- 当前 Artifact、ConfigRevision、域名、Node 和流量状态。
- 配置继承、密钥引用、版本历史和环境差异。
- 部署冻结窗口、保留版本和回滚策略。
- Preview 策略：启用、标签、上限、TTL、域名模板和外部 fork 安全。

敏感值只显示“已设置/已轮换时间”，绝不回显。

### 3.7 基础设施 `/infrastructure`

节点列表展示在线、Agent/SSH、CPU/内存/磁盘、Docker/Compose、架构、运行应用、构建/部署队列和最近异常。节点详情提供：

- 验证连接和中文诊断报告。
- 工作目录、代理、Registry 拉取、端口和证书状态。
- 运行应用与资源占用。
- 暂停调度、排空、重新验证和 Agent 升级。

验证成功只表示“可接入”，成功部署后才能显示“已验证运行”。

### 3.8 发布证据 `/releases/:id`

按一个 Release 聚合：

- Commit/PR 与 Artifact。
- BuildPlan/ConfigRevision。
- CI Checks、测试和安全扫描。
- 审批、豁免与冻结窗口。
- 环境晋级和部署结果。
- 阻断项、回滚点和审计时间线。

顶部显示结论：`可晋级 / 被阻止 / 等待审批 / 已发布 / 已回滚`，并列出决定该结论的规则。支持导出不含秘密的发布证据包。

### 3.9 发布阻断项

现有 Issue UI 收敛为部署事故和发布阻断项，至少关联 Application、Environment、Deployment、Release、严重级别、负责人和验证状态。通用研发 Issue 通过外部链接跳转，不在 Launchly 中复制完整项目管理功能。

## 4. 首次部署向导

采用可返回、可保存草稿的五步向导：

1. **来源**：GitHub App、公开 Git、Deploy Key、OCI digest 或受控模板。
2. **服务检测**：展示识别出的 monorepo 服务、Dockerfile、端口和依据。
3. **运行配置**：健康、环境变量、域名和资源限制；高级设置折叠。
4. **节点验证**：选择/添加 Node，展示完整诊断，不以“SSH 成功”代替可部署。
5. **计划确认**：展示 BuildPlan、目标 Artifact 方式、环境、预计域名和风险后再执行。

失败不得清空用户输入；可回到对应步骤修正。

## 5. Preview 体验

PR 列表展示 PR、commit、状态、URL、最后更新、到期时间和资源占用。支持手动创建、重新部署、延长 TTL 和立即清理。外部 fork 被阻止时必须解释安全原因，不能静默失败。

PR 更新显示旧 Preview 正被替换；PR 关闭后显示清理进度，清理失败进入指挥中心待办。

## 6. 权限与状态表现

- 无权限操作使用隐藏或禁用取决于是否需要解释；直达 URL 始终由后端返回不泄露资源存在性的 403/404 口径。
- Viewer 可读取授权范围内的运行和证据，不出现可用的部署、审批、变量、节点和回滚操作。
- 生产审批默认显示触发人，禁止自审时解释原因。
- 所有列表和搜索结果都必须按 Workspace/Application 权限过滤。

统一状态词：

| 类型 | 状态 |
| --- | --- |
| 执行 | 等待、执行中、成功、失败、取消、跳过 |
| 门禁 | 等待检查、通过、阻断、等待审批、已豁免 |
| 运行 | 健康、降级、不健康、未知、已停止 |
| 验收 | 未实现、代码路径、未验收、已验收 |

## 7. 设计系统

### 7.1 基础 Token

| 用途 | 值 |
| --- | --- |
| 主色 | `#0D9488` |
| 主色弱背景 | `#CCFBF1` |
| 页面背景 | `#F8F9FB` |
| 卡片背景 | `#FFFFFF` |
| 边框 | `#E5E7EB` |
| 正文 | `#111827` |
| 次要文字 | `#6B7280` |
| 成功/警告/失败 | `#059669` / `#D97706` / `#DC2626` |

状态色只表示语义。正文以 14px 系统无衬线为基准；关键运行 ID、digest 和日志使用等宽字体。卡片圆角 10–12px，密集数据区域减少不必要阴影和大面积彩色背景。

### 7.2 组件约束

当前组件库为 Element Plus，短期以主题 Token 和业务组件封装统一体验，不再引用未使用的 Ant Design Vue。优先沉淀：StatusBadge、ArtifactRef、EnvironmentLane、PipelineGraph、LogViewer、GatePanel、DiffViewer、NodeHealth、ActionRequiredCard。

### 7.3 响应式

桌面优先满足部署工作台；窄屏将检查面板折叠为抽屉，阶段图改为纵向。日志仍需全屏查看。手机端允许审批、查看状态和紧急回滚，不要求完成复杂环境配置。

## 8. 当前实现差距

基线 `a60ae26` 的顶栏、Dashboard、项目详情和部署时间线只能作为组件起点：

- 全局搜索和主部署按钮没有完整行为。
- Dashboard 的“下一步”是统计，不是任务队列。
- 项目固定八步工作流不是后端真实流水线。
- 部署详情缺 Artifact、Config、Gate、Diff、流量和回滚上下文。
- 基础设施、Preview、发布证据尚无目标体验。

在这些数据模型和 API 可用前，UI 应标记占位，不得用 Mock 伪装完成。

## 9. 维护与验收

- 页面变化同时更新本规范、路由表、原型和交付用例。
- 每个核心页面至少验收 Loading、Empty、Error、Forbidden、Partial Data 和 Mobile 状态。
- UI 验收必须使用真实 API/状态机数据；截图或静态原型不能证明功能完成。
