# Launchly 交付验收规范

> **版本**：2.4
> **生效日期**：2026-08-13
> **地位**：Launchly 功能完成、阶段退出、版本发布和对外声明的唯一验收标准。产品目标见[产品设计规范](./产品设计规范.md)，阶段计划见[项目重启路线图](./项目重启路线图.md)，当前问题见[已知问题清单](./已知问题清单.md)。

## 1. 完成状态与证据等级

### 1.1 状态用语

| 状态 | 含义 | 是否可称完成 |
| --- | --- | --- |
| 未实现 | 没有可执行路径 | 否 |
| 代码路径 | 存在代码、页面或配置，但未完成运行验证 | 否 |
| 未验收 | 局部自动化测试通过，但缺少要求的真实环境证据 | 否 |
| 已验收 | 指定 commit 在规定环境通过可复跑验收 | 仅限覆盖场景 |
| 生产可用 | 所有发布阻断用例、安全审计和恢复演练通过 | 是 |

### 1.2 证据等级

| 证据 | 能证明 | 不能证明 |
| --- | --- | --- |
| 静态检查/编译 | 类型、语法、依赖可解析 | 应用能启动、权限正确、部署可用 |
| 单元测试 | 被测函数和 Mock 契约 | 模块接线、数据库、Docker、SSH、网络 |
| 集成测试 | 真实模块/数据库的局部合同 | 外部 Git、Registry、BYOS、HTTPS |
| 镜像启动 | 生产入口、迁移、健康和 SPA 可运行 | 自动部署、并发、回滚和安全 |
| 真实 E2E | 指定版本和环境完成完整行为 | 未覆盖场景和长期稳定性 |
| 故障/恢复演练 | 明确故障下保持或恢复服务 | 其他故障类型 |

AI、人工报告或“已阅读全部代码”的自述不是证据。每项结论必须能追溯到源码、命令、运行记录或外部系统事件。

## 2. 验收记录格式

每次验收保存：

- 版本、commit、分支、工作区是否干净。
- 日期、执行者、Self-Host/未来 Cloud 形态。
- OS、CPU 架构、Node、Docker、Compose、PostgreSQL、BuildKit、浏览器版本。
- Git repository/installation、Registry、Node、域名的非敏感标识。
- 前置数据、配置摘要、BuildPlanRevision、ConfigRevision。
- 完整命令、退出码、预期、实际、部署 ID、Artifact digest。
- 脱敏日志、截图/事件引用、清理结果。
- 失败归类：产品缺陷、测试环境、外部依赖或无法确认。

密码、Token、私钥、完整连接串、环境变量值和授权 Header 不得进入记录。

## 3. R0 可信基线阻断用例

| ID | 场景 | 通过条件 |
| --- | --- | --- |
| BASE-01 | 全仓构建与测试 | API/Web/CLI 类型检查、单测和生产构建通过，命令与退出码有记录 |
| BASE-02 | 生产入口 | Docker 生产镜像成功构建；entrypoint 实际文件存在；API/Worker 各自启动并健康 |
| BASE-03 | 模块接线 | Nest 生产模式启动，无依赖注入错误；所有 Controller 可枚举并完成最小请求 |
| BASE-04 | 空库迁移 | 空 PostgreSQL 顺序执行全部 migration，schema 与 Prisma 一致 |
| BASE-05 | 升级迁移 | 从上一公开基线数据库升级；失败不启动新 API，备份可恢复 |
| BASE-06 | Workspace 隔离 | 两个 Workspace 互相无法读取/修改 Project、Environment、Variable、Deployment、Test、Issue、Release、Target |
| BASE-07 | 项目角色 | Owner/Admin/Developer/Tester/Viewer 对每个项目子资源的读写矩阵符合规范 |
| BASE-08 | DTO、唯一性与资源归属 | 未声明字段、非法状态/域名/ID 被拒绝；URL 父 ID 与资源真实父级不一致时拒绝；环境变量等同级资源的唯一性语义由数据库约束并返回明确冲突 |
| BASE-09 | 密钥静态边界 | 生产默认密钥被拒绝；日志、错误、任务 payload、审计和 API 不含明文 |
| BASE-10 | 权威交付配置 | CLI、Compose、Dockerfile、环境变量示例和 README 使用同一服务拓扑与启动语义 |
| BASE-11 | 测试保护网 | API/Web/CLI 使用全量源码统计口径达到[测试补全任务书](./测试补全任务书.md)的 R0 门槛；关键场景矩阵全部通过，且无 `.skip/.only/todo`、统计范围缩小或覆盖率忽略 |

R0 未通过前，README 必须标记为“重启/基线修复”，不能标 Beta。

## 4. 核心端到端验收

### 4.1 首次部署与 Self-Host

| ID | 场景 | 通过条件 |
| --- | --- | --- |
| E2E-01 | 空白机安装 | 空白 Ubuntu 重复执行安装，完成 migration、`/setup`、Owner、API/Worker 健康和登录 |
| E2E-02 | Node 诊断 | SSH/Agent、Host Key、Docker、Compose、架构、目录、磁盘、端口、代理、Registry 拉取逐项有真实结果 |
| E2E-03 | 既有 OCI 首次上线 | 只使用 `image@sha256`，部署到 BYOS，健康通过并获得访问地址；不登录目标机手工修复 |
| E2E-04 | 控制面运维 | status/logs/doctor/backup/restore/upgrade 可复跑，恢复后 API、Worker 和应用健康 |

### 4.2 Git、CI 与并发

| ID | 场景 | 通过条件 |
| --- | --- | --- |
| E2E-05 | GitHub Push 自动部署 | HMAC、schema、installation/repository 映射、去重、CI、构建、部署、健康和状态回写均有真实证据 |
| E2E-06 | Webhook 重放 | 同一 delivery 重放不新建部署；相同 commit 的幂等请求返回原记录 |
| E2E-07 | CI 阻断 | CI 未通过不构建/部署，GitHub 显示阻断原因和 Launchly 链接；通过后可继续 |
| E2E-08 | 部署并发 | `queue_all`、`latest_only`、`cancel_previous` 分别符合定义，无重复副作用或错误切流 |
| E2E-09 | Monorepo 路径过滤 | 只修改一个服务时，仅受影响 BuildPlan/服务进入构建部署 |

### 4.3 制品、环境与发布

| ID | 场景 | 通过条件 |
| --- | --- | --- |
| E2E-10 | 构建一次逐级晋级 | 测试、预发、生产 Deployment 引用相同 Artifact ID/digest，生产没有重新构建 |
| E2E-11 | 配置版本与差异 | 每次部署绑定 ConfigRevision；晋级前能展示非敏感差异；密钥只显示引用/变更状态 |
| E2E-12 | Release Phase 失败 | migration/初始化失败不切流量，旧版本和数据可用，失败可追溯 |
| E2E-13 | 审批与冻结 | 禁止自审、分支限制、冻结窗口和紧急豁免生效，操作全部审计 |
| E2E-14 | 发布证据 | 一次生产发布可导出 commit、Artifact、Config、Checks、测试、审批、部署和回滚点，且无秘密 |

### 4.4 流量、回滚与隔离

| ID | 场景 | 通过条件 |
| --- | --- | --- |
| E2E-15 | 同机并发多应用 | 两个应用并发部署，目录、Compose project、网络、容器、卷和路由不冲突，互不影响 |
| E2E-16 | 域名与 HTTPS | 自动签发/续期可验证；节点/代理重启后恢复；证书失败形成可操作告警 |
| E2E-17 | 健康失败 | 候选不接流量，旧版本持续可访问，Deployment 进入失败/回滚状态 |
| E2E-18 | 真实回滚 | 恢复上一 Artifact、ConfigRevision、运行清单和路由；不重新构建；回滚失败可观测 |
| E2E-19 | Worker 故障 | 部署中杀死 Worker，任务依租约安全重领，无重复构建、重复切流或孤儿状态 |
| E2E-20 | Node 故障 | Node 离线时任务安全等待/失败，恢复后按策略重试；控制面保持健康 |

### 4.5 Preview

| ID | 场景 | 通过条件 |
| --- | --- | --- |
| E2E-21 | PR Preview 创建 | 目标 PR 自动/手动获得隔离 URL、环境、配置和部署记录 |
| E2E-22 | Preview 更新 | PR 新 commit 更新 Preview；旧实例和路由按策略清理 |
| E2E-23 | Preview 回收 | PR 关闭/合并或 TTL 到期后，容器、路由、目录和临时秘密全部可证明清理 |
| E2E-24 | Preview 安全 | 外部 fork 默认无法获得受信秘密或进入生产网络；标签/配额策略生效 |

### 4.6 可观测、通知与中文体验

| ID | 场景 | 通过条件 |
| --- | --- | --- |

## 5. 阶段退出标准

| 阶段 | 必须通过 |
| --- | --- |
| R0 可信基线 | BASE-01 至 BASE-11 |
| R1 首次部署 | E2E-01 至 E2E-04 |
| R2 持续交付 | E2E-05 至 E2E-09 |
| R3 安全生产 | E2E-10 至 E2E-20 |
| R4 Preview/Monorepo | E2E-21 至 E2E-24，且 E2E-09 保持通过 |
| R5 发布治理 | E2E-13、E2E-14、E2E-25 至 E2E-28 |
| R6 多节点/Cloud | Agent 多节点、租户隔离、配额和授权的新增阻断用例；不得复用 Self-Host 证据代替 |

生产可用要求 R0–R5 的全部阻断用例通过，并完成第三方安全审计、恢复演练和发布签核。

## 6. UI 验收

核心页面必须使用真实 API 数据通过：Loading、Empty、Running、Partial Data、Failure、Forbidden、Mobile。部署工作台需证明真实阶段、日志、Gate、Artifact、Config diff、流量和回滚数据；固定步骤、Mock 图或静态截图不算完成。

## 7. 当前基线记录（`8fd41b0`，2026-08-13）

已独立确认：现有 API/Web/CLI 单元测试及 TypeScript/生产构建命令可通过。但以下事实使 R0 保持未通过：

- TEST-API-01/02 已独立验收，API/Web/CLI 行覆盖率分别为 18.66%/5.65%/10.13%。安全基础和 Environment Service 已有局部单元测试保护，但整体覆盖率和关键场景矩阵仍不足，BASE-11 保持未通过。
- API 构建输出位于 `dist/src/main.js`，现有 production/entrypoint 指向 `dist/main`。
- Dockerfile 在 BuildKit 镜像阶段执行 Web `pnpm build`，阶段缺少对应 Node/源码上下文。
- `EnvironmentService` 未注册到 `EnvironmentModule`，实际启动出现 Nest 依赖注入错误。
- Release、Issue、Test、Environment 等多个子资源接口未统一验证 Workspace/Project 归属。
- 尚无真实 Docker 镜像启动、空库/升级库、GitHub、Registry、BuildKit、SSH、HTTPS 或回滚 E2E 记录。

因此当前状态是“代码基线，R0 修复中”，不是 Beta，也没有任何可对外承诺的部署路径。
