# Launchly 已知问题清单

> **版本**：1.9
> **基线**：`a60ae26`（2026-08-13）
> **地位**：当前已确认问题的唯一集中记录。实施顺序见[项目重启路线图](./项目重启路线图.md)，完成标准见[交付验收规范](./交付验收规范.md)。
> **边界**：本清单不是待办列表；记录问题不代表已经批准修复，也不代表路线图任务已完成。

## 1. 分类和状态

### 1.1 类型

| 类型 | 含义 |
| --- | --- |
| 功能缺陷 | 当前代码的行为与明确合同不一致 |
| 安全缺陷 | 认证、授权、秘密或隔离边界存在可确认风险 |
| 工程阻断 | 构建、启动、迁移或交付链路无法继续 |
| 测试缺口 | 关键行为没有自动化或真实环境证据 |
| 架构缺口 | 当前实现与已确定的目标架构或身份模型不一致 |
| 技术债 | 当前不一定阻断，但会造成性能、维护或扩展问题 |
| 产品死路径 | 界面展示了没有真实行为或后端合同的操作 |

### 1.2 严重度

| 等级 | 规则 |
| --- | --- |
| P0 | 阻止启动/部署，或存在跨租户、秘密、认证等高风险问题 |
| P1 | 核心功能错误、重要合同断裂或明显质量风险 |
| P2 | 不阻断主链路的性能、体验和维护问题 |

### 1.3 状态

| 状态 | 含义 |
| --- | --- |
| 已确认 | 已有源码或可复跑命令证明，尚未开始修复 |
| 处理中 | 对应任务已有获准实施变更 |
| 待验收 | 修复代码存在，但对应 BASE/E2E 尚未通过 |
| 已关闭 | 修复和规定验收均通过 |
| 暂缓 | 问题成立，但当前阶段明确不处理 |

## 3. 详细证据

### KI-001：生产入口不一致

- **证据**：[API package scripts](../../services/api/package.json) 的 `start:prod` 和 [docker-entrypoint.sh](../../services/api/docker-entrypoint.sh) 使用 `dist/main`；`pnpm --dir services/api build` 实际生成 `dist/src/main.js`。
- **复现**：`pnpm --dir services/api start:prod` 返回 `MODULE_NOT_FOUND`。
- **影响**：生产 API 和 Worker 都无法按当前入口启动。
- **关闭条件**：BASE-01、BASE-02。

### KI-002：Dockerfile 阶段错误

- **证据**：[Dockerfile](../../services/api/Dockerfile) 在 `FROM moby/buildkit... AS buildkit` 后进入 `/app/apps/web` 并运行 `pnpm build`，该阶段没有 Node/pnpm，也没有复制 Web 源码。
- **影响**：生产镜像无法按当前 Dockerfile 构建。
- **关闭条件**：BASE-02。

### KI-003：Nest 模块依赖注入失败

- **证据**：[EnvironmentController](../../services/api/src/environment/environment.controller.ts) 注入 `EnvironmentService`，但 [EnvironmentModule](../../services/api/src/environment/environment.module.ts) 的 providers 没有它。
- **复现**：直接运行实际构建入口时出现 `Nest can't resolve dependencies of the EnvironmentController`。
- **影响**：即使绕过 KI-001，API 仍不能启动。
- **关闭条件**：BASE-03，并保留启动烟雾测试防止回归。

### KI-004：项目子资源授权不完整

- **证据**：[EnvironmentController](../../services/api/src/environment/environment.controller.ts)、[EnvironmentVariableController](../../services/api/src/environment/environment-variable.controller.ts)、[ReleaseController](../../services/api/src/release/release.controller.ts)、[IssueController](../../services/api/src/issue/issue.controller.ts)、[TestCaseController](../../services/api/src/testcase/testcase.controller.ts) 和 [TestRunController](../../services/api/src/testcase/testrun.controller.ts) 的多个读取/写入仅按 URL ID 查询，没有统一调用项目资源授权策略。
- **影响**：已登录用户知道其他 Workspace/Project 的 ID 时，可能读取或修改不属于自己的资源。
- **关闭条件**：BASE-06、BASE-07；必须使用双 Workspace 集成测试，不接受仅 Mock 角色守卫。

### KI-005：输入合同与资源归属校验不完整

- **证据**：Release、Issue、TestCase、TestRunCase 和部分 Component 接口仍以 `@Body() body: any` 接收输入；部分接口 URL 含 `projectId`，Service 却只按子资源 ID 更新。`TestRunCase.result` 没有受限 DTO/枚举校验。
- **影响**：全局 ValidationPipe 无法约束这些 body，父项目 ID 可能只起展示作用。
- **关闭条件**：BASE-08。

### KI-006：自动化覆盖不足

- **证据**：详见[测试补全任务书](./测试补全任务书.md)基线。TEST-API-01 至 06 和 TEST-API-07A/07B 已覆盖安全基础及 Environment、Project、Release、Notification、Test、DeployTarget、Worker 和首批 Runner 边界，但当前 API/Web/CLI 行覆盖率仍仅 52.82%/5.65%/10.13%；SSH/Shell Runner、Project 主 Service/Controller 和 24 个 Web 页面等关键区域仍低覆盖或为 0%。
- **影响**：测试数量不能代表核心路径受到保护，KI-003 这样的启动错误未被现有测试发现。
- **关闭条件**：BASE-11 和测试任务书的场景矩阵全部通过。

### KI-007：缺少集成与真实 E2E

- **证据**：API 已有 28 个 Jest suite，但现有 `test:e2e` 配置没有实际 E2E 用例。没有真实 PostgreSQL、Docker 镜像、GitHub、Registry、BuildKit、SSH、HTTPS 或回滚记录。
- **影响**：单元测试和编译通过不能证明系统能启动或部署。
- **关闭条件**：R0 对应 BASE 和后续 E2E 分阶段完成，不能以覆盖率代替。

### KI-008：前后端 API 合同漂移

- **证据**：
  - [Web API client](../../apps/web/src/api/client.ts) 请求通知未读数和单条已读，但 [NotificationController](../../services/api/src/notification/notification.controller.ts) 没有这两个路由。
  - [ReleaseDetailPage](../../apps/web/src/pages/ReleaseDetailPage.vue) 读取 `gatesRes.data.results`，后端 [GateCheckService](../../services/api/src/release/gate-check.service.ts) 返回 `gates`。
  - Web 发送 Issue `targetStatus`，后端 [IssueController](../../services/api/src/issue/issue.controller.ts) 接收 `toStatus`。
- **影响**：页面操作出现 404、空 Gate 或状态转换失败。
- **关闭条件**：R0-09 的合同测试通过。

### KI-009：Web 登录边界不完整

- **证据**：[router/index.ts](../../apps/web/src/router/index.ts) 没有全局路由守卫；[auth store](../../apps/web/src/stores/auth.ts) 只在本次登录时保存 user/workspace，没有从已有 token 恢复会话。
- **影响**：未登录用户可进入受保护页面壳层，刷新后 UI 身份丢失；后端仍会拒绝 API，但体验与权限显示不可靠。
- **关闭条件**：R0-09 集成测试；Token 存储策略纳入 R0-08 安全决策。

### KI-010：Token 用途未隔离

- **证据**：[AuthService](../../services/api/src/auth/auth.service.ts) 使用同一 JWT secret 签发 Access/Refresh Token，payload 没有 `typ`/`aud`，`refresh()` 只验证签名，因此有效 Access Token 也能进入刷新路径。当前没有 refresh token 哈希、撤销或重放记录。
- **影响**：Token 生命周期和撤销边界弱于产品需要。
- **关闭条件**：R0-08 安全设计和相应认证集成测试通过。

### KI-011：CORS 默认配置冲突

- **证据**：[main.ts](../../services/api/src/main.ts) 默认 `origin: '*'`，同时 `credentials: true`。
- **影响**：浏览器 credential CORS 语义冲突，生产环境也容易因未显式配置来源而过度开放。
- **关闭条件**：R0-08 明确开发/生产来源策略并增加配置测试。

### KI-012：GitHub 身份映射不稳定

- **证据**：[WebhookService](../../services/api/src/git/webhook.service.ts) 枚举配置了 repositoryUrl 的项目并做字符串归一化匹配，而不是以 GitHub installation ID + repository ID 定位项目。
- **影响**：仓库转移、URL 别名或多 Workspace 配置可能产生误匹配。
- **关闭条件**：R2-01、R2-02 和 E2E-05/06。

### KI-013：列表性能和分页缺失

- **证据**：[DeploymentService](../../services/api/src/deployment/deployment.service.ts) 列表没有 take/cursor/limit；`enrichDeployments()` 对每条记录再次查询用户和环境。其他多个列表也无分页。
- **影响**：数据增长后请求和数据库查询数线性放大。
- **关闭条件**：建立统一分页合同和查询数测试后另行排期。

### KI-014：可见但不可用的 UI 操作

- **证据**：[AppLayout](../../apps/web/src/pages/AppLayout.vue) 的全局搜索只有输入状态；[SettingsPage](../../apps/web/src/pages/SettingsPage.vue) 保存逻辑仍是 TODO。
- **影响**：界面暗示存在能力，但用户操作没有结果。
- **关闭条件**：删除死入口或实现并通过 UI/API 验收。

### KI-015：Web 初始包过大

- **证据**：当前生产构建中 `index` JavaScript 约 1,090 kB（gzip 约 362 kB），Vite 输出超过 500 kB 的 chunk 警告。
- **影响**：弱网络或 NAS 控制面首次加载较慢。
- **关闭条件**：设定性能预算、拆包并在 CI 记录产物大小；不作为当前 R0 P0 阻断。

### KI-016：Environment Variable 重复 key 静默覆盖

- **证据**：[EnvironmentVariable Schema](../../services/api/prisma/schema.prisma) 只有 `@@index([environmentId])`，没有 `@@unique([environmentId, key])`；[EnvironmentVariableService](../../services/api/src/environment/environment-variable.service.ts) 创建前也不检查重复 key。[RemoteSshRunner](../../services/api/src/worker/runners/remote-ssh.runner.ts) 通过 `Object.fromEntries` 把变量数组转为对象，重复 key 会被后出现的记录静默覆盖。
- **影响**：同一环境可能保存多个同名变量，实际部署值取决于未声明顺序，可能把错误的配置或秘密注入应用。
- **关闭条件**：确定重复 key 的产品语义；增加数据库唯一约束与迁移、明确冲突响应，并用 Service 测试和真实 migration 验收覆盖。

### KI-017：GitHub SSH 仓库名被截断

- **证据**：[RepositoryHintsService](../../services/api/src/project/repository-hints.service.ts) 的 `GITHUB_SSH` 使用未锚定的非贪婪仓库段 `([^/]+?)`，而尾部 `.git` 又是可选项。`git@github.com:acme/app.git` 和无后缀形式都会只捕获 `a`，从而请求 `raw.githubusercontent.com/acme/a/...`。TEST-API-03 已通过隔离 fetch Mock 复现。
- **影响**：GitHub SSH 仓库无法得到正确的 package.json/README 自动检测结果，私有仓库引导和默认构建参数可能失败。
- **关闭条件**：修正并锚定 SSH URL 解析；单测必须改为断言完整仓库名，且在受控 GitHub 仓库完成真实联调后通过 E2E-05。

### KI-018：未知最低项目角色会降低授权要求

- **证据**：[ProjectAccessService](../../services/api/src/project/project-access.service.ts) 使用 `(levels[minimumRole] || 1)`；任何拼错或未知的 `minimumRole` 都会变成 VIEWER。当前调用点传入常量，但授权助手本身会在未来调用错误时静默放宽权限。TEST-API-03 的五级矩阵和未知角色用例已复现该行为。
- **影响**：新增接口若把 ADMIN/DEVELOPER 等角色名拼错，不会拒绝或报配置错误，而可能允许 VIEWER 访问，形成隐蔽的授权回归。
- **关闭条件**：将角色改为共享的受限类型或枚举，运行时对未知值 fail closed；通过单元矩阵和双 Workspace/角色集成测试。

### KI-019：仓库自动检测未接入项目流程

- **证据**：[RepositoryHintsService](../../services/api/src/project/repository-hints.service.ts) 实现了 `infer()` 和 `fillBlanksFromRepository()`，但 [ProjectModule](../../services/api/src/project/project.module.ts) 没有注册该 Service，仓库内也没有生产调用方；[ProjectService](../../services/api/src/project/project.service.ts) 直接保存 DTO 字段。当前实现还会在 package.json 缺少 start script 时推断 `npm start`/默认 3000，且不会推断 healthCheckPath。
- **影响**：代码和测试看似存在仓库检测能力，实际创建/更新项目不会使用它；若未来直接接入，当前默认值还可能给出不可执行的启动提示。
- **关闭条件**：先明确自动检测的产品合同及覆盖优先级，再将其接入创建/导入流程或删除死代码；用 API 合同测试和真实仓库验收证明结果进入项目配置。

### KI-020：空 Release Gate 状态会 fail open

- **证据**：[ReleaseService](../../services/api/src/release/release.service.ts) 只过滤 `gateStatus.gates` 中未通过且未豁免的项目。当 GateCheck 返回 `{ gates: [], allPassed: false }` 时，未解决失败数为 0，Service 仍把 Release 更新为 `PUBLISHED`，并把 gateStatus 写成 `EXEMPTED`。TEST-API-04 已用固定时间和完整 update 断言复现。
- **影响**：门禁服务返回不完整状态、竞态或未来新增异常分支时可能绕过发布阻断；“没有可用 Gate 结果”被错误等同于“全部已豁免”。
- **关闭条件**：发布必须显式要求有效且一致的 Gate 结果；空集合、`allPassed=false` 或结构矛盾一律 fail closed，并通过 Release Service、合同和真实发布门禁测试。

### KI-021：TestRun 状态与结果集合不完整

- **证据**：[TestService](../../services/api/src/testcase/test.service.ts) 创建 0 用例 Run 时不设置完成状态，因 Schema 默认而保持 `PENDING`；counter 更新对空数组执行 `every()` 却得到 true 并写成 `COMPLETED`。同时任意非 `PENDING` 字符串都会被视为完成，但只有 PASSED/FAILED/SKIPPED 进入计数。TEST-API-04 已从公开方法复现三种行为。
- **影响**：相同空 Run 可处于互相矛盾的状态；非法 result 能让 Run 完成且三个计数不等于 totalCases。GateCheck 只依据 failedCases，可能进一步把无效测试结果当作“所有测试通过”。
- **关闭条件**：定义空用例唯一语义；使用受限 result 状态机并校验计数不变量，拒绝未知值；补 Service、DTO、数据库约束和 Release Gate 集成测试。

### KI-022：共享 Prisma 测试替身不完整

- **证据**：[prisma-mock.ts](../../services/api/test/helpers/prisma-mock.ts) 的模型列表缺少 `projectMember`，通用模型方法缺少 `updateMany`、`createMany`、`upsert` 等。TEST-API-02/03/04 已多次在 spec 内通过 `as any` 手工补接口。
- **影响**：重复样板增加测试误配和假阳性风险，类型检查无法证明 Mock 与实际 Prisma 调用面一致。
- **关闭条件**：按当前 Schema 和已用方法补齐类型化共享 Mock，迁移现有手工补丁，并保持所有已验收测试通过。

### KI-023：DeployTarget 更新合同不完整

- **证据**：[DeployTargetService](../../services/api/src/target/deploy-target.service.ts) 的 update 只拒绝 `root` 和 `PASSWORD`，会把 `OAUTH` 等未知认证方式、空 credential 和空 Host Key 写入数据库；[UpdateDeployTargetDto](../../services/api/src/target/dto/update-deploy-target.dto.ts) 也未限制 authMethod、username、privateKey 和 hostKey 的格式/非空语义。TEST-API-05 已分别通过公开 update 方法和 Prisma/Secret Mock 的持久化断言复现。
- **影响**：部署目标可从创建时的 KEY-only、非 root、固定 Host Key 安全状态退化为不可验证或含无效凭据的状态；非法用户名还会延迟到真实 SSH 时才失败。
- **关闭条件**：建立共享且受限的认证/用户名/Host Key/私钥更新 DTO 与 Service 不变量，部分更新必须结合现有记录验证最终状态；通过 Service、真实 ValidationPipe 合同测试和 E2E-02。

### KI-024：SSH 验证异常与资源生命周期不完整

- **证据**：[DeployTargetService.verify](../../services/api/src/target/deploy-target.service.ts) 在 `client.on('ready')` 回调内直接调用可能抛出异常的 workRoot 正规化，没有在回调内捕获并 reject；TEST-API-05 以持久化的 `/` 复现该异常同步逃逸事件回调，原 verification Promise 仍待定。`client.on('error', reject)` 路径也没有调用 `client.end()`，同一测试通过 Client Mock 证明连接错误返回 FAILED 时释放次数为 0。
- **影响**：遗留/异常数据可能让验证请求悬挂并把异常抛到事件循环；连接失败可能遗留 SSH 资源。单元测试无法证明真实 ssh2 socket 的最终清理行为。
- **关闭条件**：所有 ready/exec/error/close 路径统一进入可控的 settle/cleanup 流程，异常只返回一次、Client 最多关闭一次；补单元测试并通过真实节点的 E2E-02 失败注入。

### KI-025：Worker 输入和任务类型 fail open

- **证据**：[WorkerService](../../services/api/src/worker/worker.service.ts) 对无法映射的 taskType 直接把 Task 写为 `SUCCEEDED`；`parsePayload()` 只捕获 JSON 语法错误，不拒绝数组、字符串、数字和 JSON `null`。[WorkerService spec](../../services/api/src/worker/worker.service.spec.ts) 已通过公开 `poll()` 分别证明未知类型不调用 Runner 且成功，以及四类非对象值原样进入 Runner；TEST-API-07A/07B 进一步证明 RunnerFactory/TemplateSourceRunner 会因 null/缺失 payload 抛 TypeError。
- **影响**：拼错或未来未注册的任务可能被静默吞掉；Runner 可能收到不符合对象合同的 payload 并在更深层产生难以定位的错误。
- **关闭条件**：任务类型使用单一受限合同并对未知值 fail closed；payload 解析后必须验证为对象且符合对应任务 schema，补充单元、合同和 E2E-19 测试。

### KI-026：空阶段集合会完成部署

- **证据**：[WorkerService.checkAndUpdateDeployment](../../services/api/src/worker/worker.service.ts) 对 StageLog 使用 `logs.every(...)`；空数组也返回 true。TEST-API-06 已证明没有任何 StageLog 时 Deployment 仍写成 `SUCCEEDED`，Environment 同时写成 `active` 并绑定为当前部署。
- **影响**：阶段记录缺失、创建失败或数据异常时，系统可能把从未完整执行的部署暴露为成功环境。
- **关闭条件**：部署完成必须校验非空且与该部署类型的预期阶段集合完全一致；缺失、重复、未知或非终态阶段一律 fail closed，并通过状态机单测和 E2E-19。

### KI-027：Worker 失败、重试与超时状态不一致

- **证据**：TEST-API-06 证明 Runner 返回失败后 StageLog 先写 `FAILED + finishedAt`，随即又写 `RUNNING` 且不清除 `finishedAt`；Runner 抛异常时 StageLog 可能一直为 `RUNNING`，即使 Task/Deployment 已失败；超时重试完全不写 StageLog；无 message 异常会记录字面量 `undefined`。同一测试还证明首个超时任务更新失败会中断整个批次，过期 RUNNING 租约重领不增加 attempts。
- **影响**：控制面展示的 StageLog、Task 和 Deployment 终态互相矛盾；单点数据库错误会阻断其他超时任务；租约反复过期可能绕过最大重试语义。
- **关闭条件**：定义并原子化 Task/StageLog/Deployment 状态转换和 attempts 语义；异常与超时统一生成可追溯终态，批处理隔离单任务失败，并通过并发单测、数据库集成和 E2E-19 故障注入。

### KI-028：Worker 重试路径泄露原始错误

- **证据**：[WorkerService](../../services/api/src/worker/worker.service.ts) 只在 `writeStageLogFinal()` 调用 `CommandExecutor.sanitize()`；`handleTaskFailure()` 随后把原始 `errorMessage` 传给未脱敏的 `writeStageLog()`，同时直接写入 Logger。TEST-API-06 以 `password=hunter2` 证明 FAILED 写已脱敏，但紧随其后的 RUNNING retry 写和运行日志重新出现明文；TEST-API-07B 进一步证明 GitRunner 的 `errorMessage` 和 BuildkitRunner 的失败 stdout/stderr 可携带未脱敏秘密进入该边界。
- **影响**：命令错误中携带的密码、Token 或连接信息可能进入数据库 StageLog 和生产日志，形成秘密暴露与长期留存。
- **关闭条件**：所有持久化和 Logger 边界统一先脱敏，禁止原始 Runner 错误越过边界；补秘密模式矩阵、日志捕获测试和 BASE-09 验收。

### KI-029：自动回滚阶段顺序冲突

- **证据**：[WorkerService.scheduleAutomaticRollback](../../services/api/src/worker/worker.service.ts) 固定创建 `stepOrder: 5` 的 ROLLBACK；[DeploymentService](../../services/api/src/deployment/deployment.service.ts) 对启用 Bootstrap 的部署同样把 HEALTH_CHECK 设为 stepOrder 5，而日志查询只按 stepOrder 升序。TEST-API-06 已断言回滚实际写入 5。
- **影响**：同序阶段的显示和处理顺序不稳定，部署时间线可能把健康检查与回滚排列错误。
- **关闭条件**：阶段顺序来自同一权威计划或使用稳定的复合排序/独立回滚序列；补两类部署的时间线和回滚测试。

### KI-030：JSON 结构日志秘密未脱敏

- **证据**：[CommandExecutor.sanitize](../../services/api/src/worker/runners/command.executor.ts) 的通用 key/value 正则要求字段名单词后直接出现冒号或等号，无法跨过 JSON 字段名后的引号。TEST-API-07A 通过公开 `sanitize()` 证明 `{"password":"hunter2","token":"plain-token","api_key":"api-secret"}` 原样返回，三个秘密均仍存在。
- **影响**：Runner、命令或外部工具输出 JSON 错误/配置时，密码、Token 和 API Key 可能进入 StageLog、Worker 日志或审计留存；现有“已调用 sanitize”不能证明秘密安全。
- **关闭条件**：使用结构感知或覆盖 JSON/文本边界的统一脱敏器；建立字段名、大小写、引号、转义、多行、URL、PEM 和嵌套对象矩阵，并通过 BASE-09 日志捕获验收。

### KI-031：OCI 制品与部署引用非原子

- **证据**：[OciImageRunner.execute](../../services/api/src/worker/runners/oci-image.runner.ts) 和 [BuildkitRunner.execute](../../services/api/src/worker/runners/buildkit.runner.ts) 均先独立执行 `artifact.upsert`，再执行 `deployment.update`，没有事务。TEST-API-07A/07B 通过公开 `execute()` 和调用顺序证明 Artifact upsert 成功后，Deployment update 抛错会原样退出，前一写入没有回滚边界。
- **影响**：数据库故障或锁冲突可留下已存在 Artifact、但 Deployment 未绑定 `artifactDigest` 的中间/最终不一致状态；若重试耗尽，控制面与执行面可能对可用制品产生不同判断。
- **关闭条件**：两次写入进入同一数据库事务，或定义可恢复且幂等的显式状态机与补偿；补数据库集成测试并通过 E2E-10/19 故障注入。

### KI-032：Runner 文件路径和标识符缺少边界校验

- **证据**：[GitRunner](../../services/api/src/worker/runners/git.runner.ts)、[TemplateSourceRunner](../../services/api/src/worker/runners/template-source.runner.ts) 和 [BuildkitRunner](../../services/api/src/worker/runners/buildkit.runner.ts) 直接把 `ctx.refId` 传给 `path.join(BUILD_ROOT, ...)`；Git 的私钥/known_hosts 文件名和 BuildKit 镜像 tag 也直接包含该值。TEST-API-07B 通过完全 Mock 的 fs 证明 `../escape-1` 会把工作路径规范化为 `/tmp/escape-1`，Git/Template 随后会递归删除或写入该目录，BuildKit 也会使用逃逸路径和未校验 tag。
- **影响**：被污染的任务数据可能让 Worker 删除、覆盖或读取构建根目录之外的文件，并生成非法或误导性的镜像引用。
- **关闭条件**：refId 使用受限 ID schema；所有工作路径解析后必须验证仍位于任务专属根目录，临时文件使用不可预测的专属目录；镜像 tag 使用独立白名单编码。补路径穿越单测和隔离文件系统故障测试。

### KI-033：指定 Git revision 失败后静默使用分支头

- **证据**：[GitRunner.execute](../../services/api/src/worker/runners/git.runner.ts) 在 clone 后对 `commitSha` 执行 fetch/checkout，但二者任一返回非零只写 warning，最终仍返回 `success: true` 和 clone 结果。TEST-API-07B 已分别证明 fetch 失败时不再 checkout、checkout 失败时也不失败任务。
- **影响**：部署记录声称对应指定 commit，实际构建内容却可能是分支当前头，破坏制品可追溯性、审批证据和回滚可信度。
- **关闭条件**：只要请求了 commitSha，fetch 和 detached checkout 任一步失败都必须 fail closed；构建前读取并核对实际 HEAD，Artifact 保存并验证解析后的 commit，通过真实 Git E2E-05/10。

### KI-034：Deploy Key 临时秘密清理不完整

- **证据**：[GitRunner.clone](../../services/api/src/worker/runners/git.runner.ts) 在内部写入私钥和 known_hosts，只有整个 clone Promise 成功返回后，外层才取得两个路径并在 finally 清理。TEST-API-07B 证明第二次写入或 `executor.execFile` 抛错时外层路径仍为 undefined，先前已写入的文件不会调用 unlink。
- **影响**：Git 进程、磁盘或权限异常可能把明文部署私钥长期留在 Worker 文件系统，后续任务或本机进程可读取。
- **关闭条件**：先建立任务专属临时目录和外层可见的清理句柄，再写秘密；所有部分写入、spawn、超时和取消路径统一 finally 清理并验证权限，补 BASE-09 文件系统检查。

### KI-035：BuildKit digest 校验不完整

- **证据**：[BuildkitRunner.readDigest](../../services/api/src/worker/runners/buildkit.runner.ts) 只要求字符串以 `sha256:` 开头。TEST-API-07B 通过 metadata 公开路径证明 63/65 字符和包含非十六进制字符的 digest 均被写入 Artifact 与 Deployment。
- **影响**：无效制品标识可进入控制面，导致晋级、拉取、去重和回滚失败，也削弱对不可变制品的验证。
- **关闭条件**：与 OCI Runner 共享严格的 `sha256:[0-9a-f]{64}` 解析器并统一大小写/格式；数据库写入前验证，补 metadata、Registry 和 E2E-10 合同测试。

### KI-036：构建目录清理配置可进入危险值

- **证据**：[BuildCleanupService](../../services/api/src/worker/cleanup/build-cleanup.service.ts) 直接 `parseInt()` 环境变量。TEST-API-07B 证明负数会把 cutoff 推到未来并删除当前目录，非数字会令清理永久失效，`7days` 会被静默接受为 7。
- **影响**：错误配置可能删除仍在构建的目录，或让制品上下文无限堆积耗尽磁盘。
- **关闭条件**：启动时严格校验有限正整数范围，非法配置 fail closed；清理时排除活跃任务并使用租约/锁，补并发构建和磁盘故障测试。

### KI-037：隐式 Dockerfile 端口未校验

- **证据**：[BuildkitRunner.implicitDockerfile](../../services/api/src/worker/runners/buildkit.runner.ts) 对 payload 直接 `Number()` 后写入 `EXPOSE`。TEST-API-07B 证明非数字、负数和 65536 分别生成 `EXPOSE NaN`、`EXPOSE -1` 和 `EXPOSE 65536`。
- **影响**：自动生成的 Dockerfile 无效，失败直到远端构建阶段才暴露，错误信息与用户输入合同脱节。
- **关闭条件**：任务 payload/BuildPlan 在入队前和执行前统一校验 1–65535 整数；非法值不得生成或调用 BuildKit，并补 DTO、任务合同和 BASE-08 测试。

## 4. 维护规则

1. 新问题必须包含可复跑命令或源码链接；只有猜测时标记“待复核”，不能写成已确认。
2. 修复开始后只更新状态和关联任务，不在本清单展开实施方案。
3. 修复提交存在但验收未通过时只能标记“待验收”。
4. 关闭时补充 commit、验收 ID 和证据链接；不得删除历史编号。
5. 测试失败暴露的新缺陷先创建 `KI-###`，不能让测试执行者顺手修改业务代码。
